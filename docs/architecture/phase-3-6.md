# Phases 3–6 — Data editing, semantic completion, transfer and table design

This block closes the core database-IDE surface: edit rows safely, complete SQL with real scope,
move data in and out, and create tables from a form.

## Phase 2 addendum — script files

- A console now remembers the `.sql` file it came from (`ConsoleTab.path`). **File → Open SQL
  Script…** (`Ctrl/⌘+O`), **Save** (`Ctrl/⌘+S`) and **Save As** (`Ctrl/⌘+Shift+S`) are also in the
  command palette.
- Top-level relative `@include` resolves next to that file, not in Documents. Restoring a workspace
  keeps the path, so includes still work after a restart.
- The tab shows a dot while it has unsaved edits and asks before discarding them.
- Saving never writes to an arbitrary path from the renderer. `DesktopService` keeps the set of
  paths the user opened or chose in a save dialog; anything else (including a restored path after a
  restart) opens the native dialog first.

## Phase 3 — Data editor

Inline editing, add/delete row, paging, `WHERE`/`ORDER BY` and the transactional Submit already
existed. This phase adds the safety and visibility around them:

- Pending changes are generated by `src/core/gridEdit.ts` instead of inside the component. It
  groups edits per row into one UPDATE, skips edits on deleted rows, addresses rows by primary key
  (`IS NULL` when the key is null), generates INSERTs in grid order and leaves blank cells to the
  column defaults.
- A **Preview** button shows the exact SQL that Submit will run.
- On a protected profile (Test/Prod, `confirmsWrites`), Submit asks for confirmation and includes
  the first statements in the prompt. Previously the grid wrote directly through `db.submit` and
  skipped the console's profile checks.
- `db.submit` still runs the statements in one transaction when it opened it, rolls back on error
  and rejects an UPDATE/DELETE that affects zero rows.

## Phase 4 — Semantic completion

`src/core/sqlComplete.ts` already resolved aliases, table qualifiers, schema qualifiers, INSERT
column lists and foreign-key JOINs. This phase adds statement-local CTE scope:

- `cteTables` extracts `WITH name [(cols)] AS (...)` definitions (quoted bodies and comments are
  skipped), derives the projected columns from the first SELECT when no explicit list is given and
  exposes them as virtual tables.
- CTEs shadow real tables with the same name, so `with orders as (...) select * from orders o where o.`
  offers the CTE columns, not the physical table's.
- Multiple CTEs, explicit column lists and quoted `)` inside a body are covered by tests.

## Phase 5 — Data transfer

Export already covers CSV/TSV/pipe/semicolon/JSON/INSERT/XLSX. Import is new:

- **Database → Import Data…** (`Ctrl/⌘+Shift+I`) opens a wizard with two sources:
  - a file: CSV/TSV/TXT (delimiter sniffing), JSON (array of objects, `{ data: [...] }` or a single
    object), `.sql` script, or the first/selected sheet of an XLSX workbook;
  - another data source: pick a connection and table, read it in pages (cap 50,000 rows) and map it
    to the target.
- Target: connection, schema and table from the introspected model. Required columns that are not
  mapped block the import with a list.
- Mapping starts from same-named columns (case-insensitive) and every target column can be skipped
  or pointed at any source column.
- Preview shows the first generated multi-row INSERT and how many statements will run.
- CSV empty fields become NULL; JSON nested values are serialized; XLSX dates become ISO strings.
- Imports run in blocks of 200 rows through `db.submit`, so a failure reports how many rows were
  imported before it. SQL scripts run through the same transactional submit.
- Protected profiles ask for confirmation before writing.

New dependency: `xlsx` 0.18.5 (SheetJS, Apache 2.0) for reading workbooks. Export continues to use
the project's own XLSX writer.

## Phase 6 — Table designer and ER

The ER diagram already existed; the designer was a tab type without a view. It now has:

- `DesignerEditor`: schema, table name and a column grid (name, type with per-dialect suggestions,
  not null, primary key, unique, default), add/remove rows and a live `CREATE TABLE` preview.
- Creation runs through `db.execute`, refreshes the model, closes the designer and opens the new
  table in the data editor.
- Entry points: **Database → New Table…** (`Ctrl/⌘+Alt+N`) and the command palette.
- DDL is generated by the existing tested `createTableSql` (`src/core/ddl.ts`), including composite
  primary keys.

## Verification

- `npm run verify`: typecheck, dependency-cruiser, 531 tests passed / 42 skipped, production build.
- New tests: `gridEdit.test.ts` (grouping, deletes, inserts, null keys), `dataImport.test.ts` (CSV,
  JSON, XLSX round-trip, mapping, INSERT chunking), `sqlComplete.test.ts` (CTE scope, shadowing,

- Manual Wayland smoke still covers the console; the import wizard and designer use native dialogs
  or file writes and are covered by unit tests.

## Deliberate limits

- Grid editing needs a primary key; views and keyless tables stay read-only.
- Import holds the parsed rows in the renderer; very large files are capped by the 64 MB read limit
  and 50,000-row copy cap.
- The copy source reads tables with `SELECT *`, without a column or row filter UI.
- The designer creates tables; altering an existing table is not implemented yet.
- XML/HTML/Markdown/DbUnit import and export are still pending.
